# Отдельные моды в Windows workspace: заявления, реализация, улучшения

Дополнение к [общему аудиту](AUDIT_ALL_MODS.md). Проверены каталоги `mod-b4it-hello`, `mod-b4it-overlay`, `mod-repo`, `repos/mod` внутри `C:\Users\spoter.LOCAL\Desktop\dsh-workspace`.

Это **3 самостоятельные реализации в 5 Python-файлах**. Все пять файлов прошли compile-only на **CPython 2.7.18** без импорта игры. Три hello-копии совпадают после нормализации CRLF/LF. Сторонний исходный проект XVM и инструменты разработки не выдаются за проверенные авторские моды этой коллекции.

Исходники отдельных модов не изменялись. Для анализа получены копии в `/home/spoter/wot-mods-audit/windows-extra`; ссылки ниже относительны Windows workspace. Готовая `.pyd` у overlay в обследованном проекте не найдена. Rust build/установка/DirectX hooks не запускались.

## 1. mod_b4it_hello

**Где:** `mod-b4it-hello/mod_b4it_hello.py`, `mod-repo/mod_b4it_hello.py`, `repos/mod/mod_b4it_hello.py`. Версия `v1.0 (2026-08-27)`.

- **Заявлено:** минимальный приветственный мод; README и исходник описывают сообщение «Привет!» при загрузке ангара.
- **Реализовано:** подписка на `AppLifeCycleEvent.LOBBY_VIEW_LOADED`, `SystemMessages.pushMessage(..., SM_TYPE.GameGreeting)` и запись LOAD_MOD в лог (`:3–15`). Никакой иной функциональности нет; три копии не являются тремя разными продуктами.
- **Проверено EU/RU:** событие есть в `gui/shared/events.py` (EU:101, RU:99), `GameGreeting` и `pushMessage` — в `gui/SystemMessages.py` (EU:16,126; RU:15,123). Runtime-показ сообщения не проверялся.
- **Минимальная доработка:** один canonical source, установка только одной копии; определить, показывать сообщение каждый вход в ангар или один раз за сессию.
- **Улучшение:** идемпотентная подписка, снятие listener при завершении/перезагрузке, понятный лог без дублирования сообщений.
- **Более правильный путь:** сохранить как маленький проверочный мод для стенда загрузки Python2, а не развивать отдельный пользовательский продукт. Никакого GUI framework или сервера для приветствия не нужно.
- **Приоритет:** P1 как безопасный smoke-test стенда; P3 как самостоятельная функция. Изменения не выполнялись.

## 2. mod_b4it_overlay

**Где:** `mod-b4it-overlay/python/mod_b4it_overlay.py`, `rust/src/*`, `scripts/build_pyd.ps1`, `scripts/install.ps1`. Версия Python-части `v0.1 (2026-08-27)`.

### Заявлено

Комментарии `python/mod_b4it_overlay.py:2–6`, README и UI описывают текст поверх кадра, HTML-подмножество, цвет/шрифт/тень, HDR/цветовое пространство и перемещение Ctrl+Alt+мышью; Python работает совместно с Rust-модулем `b4it_overlay.pyd`.

Фраза «только рисует текст, игровую память не читает» — заявление автора, **не результат независимого аудита всех native hooks или подтверждение правил игры**.

### Фактически реализовано

- Python-парсер `<b>/<i>/<u>/<font>/<br>`, JSON spec, настройки через `g_gui`, запрос UI scale (`:28–138,141–255,265–292`).
- Native import защищён try/except (`:20–25`); без `.pyd` фактической отрисовки нет, `_push_spec` возвращается сразу (`:295–301`), `_on_ready` не инициализирует renderer (`:328–336`). Наличие Python-кода не означает готовый overlay.
- FFI действительно ориентирован на **CPython 2.7 C API x64**, не Python3: `rust/src/ffi.rs:31–58` содержит `python27`, `Py_InitModule4_64`, `PyString_FromString`. Это ещё не доказательство ABI-совместимости с конкретной сборкой игрового движка.
- `Config.data` создаётся только при наличии `g_gui` (`:191–194`); затем `build_spec` безусловно читает `config.data` (`:265–266`). Таким образом, optional GUI fallback не полноценен, если native модуль есть, а GUI отсутствует. Исключения ловятся, но полезной конфигурации renderer это не создаёт.
- `_poll_loop` самопланируется каждые 0.25 секунды, callback ID/остановка отсутствуют (`:311–325`); повторная инициализация и завершение игры требуют контроля lifecycle.
- `install.ps1:5` по умолчанию указывает `D:\Games\World_of_Tanks_EU`, хотя D: на обследованной VM — DVD. Он копирует Python даже без `.pyd` и затем печатает «Installed» (`:25–34`): это частичная установка, а не проверенная готовность.

### Что доработать минимально

1. Не считать отсутствие native компонента успешной установкой; проверять полный манифест до копирования.
2. Явно инициализировать defaults независимо от GUI и ограничить доступность UI соответствующей capability.
3. Один контролируемый цикл опроса, ID callback, stop/unsubscribe, защита от повторного start.
4. Проверить HTML escaping/переносы/несовпавшие теги, нормализованные координаты и invalid config без native side effects.

### Что улучшить / альтернативный путь

**Предлагается, не реализовано:** для простого текста и переноса прежде оценить существующий `g_guiFlash`/клиентскую панель вместо Rust/DirectX-инжекта. Это сохраняет Python 2.7.18 бизнес-логику, уменьшает число toolchain/ABI/hooks и стоимость каждого патча игры. Возможности HDR native renderer не объявляются эквивалентными Flash: если они действительно нужны, это отдельный обоснованный проект и отдельное решение по допустимости native компонента, а не «быстро обновить мод».

**Приоритет:** P3 для текущей минимальной Python2-only актуализации. Не смешивать экспериментальную native-систему с восстановлением общего GUI; не собирать автоматически.

## 3. mod_b4it_tracers

**Где:** `repos/mod/mod_b4it_tracers.py`. Версия `v1.0 (2026-08-29)`.

### Заявлено

Docstring `:4–25` обещает 3D-траектории «из всех источников», собственные/чужие/рикошеты, обратный трассер по попаданию и маркеры взрывов. Там же заявлены «легальный мод-API», отсутствие чтения памяти/DirectX и достаточность данных для полной траектории.

### Что реализовано и где разрыв

- Геометрия из сегментов BigWorld.Model, события Avatar, срок жизни и лимиты 48 траекторий / 64 маркера (`:47–60,63–119,168–241`). Это попытка реализации, а не проверенный результат отрисовки.
- **Доказанная ошибка EU:** `showTracer` передаёт `gravity` как скаляр FLOAT32; `entity_defs/Avatar.def:412–427`, `ProjectileMover.py:55–71` преобразует его в `Math.Vector3(0.0, -gravity, 0.0)` для debug drawer. В моде `_parabolaPoints:143–149` вызывает `gravity.scale(...)` непосредственно. Для скаляра это AttributeError; `patchedShowTracer:315–321` глотает исключение и оставляет оригинальный трассер, но дополнительная траектория не строится.
- **Доказанная несовместимость RU:** обёртки `:315` и `:330` фиксируют EU-сигнатуры. RU `Avatar.showTracer:1556` принимает 9 аргументов после self, а обёртка требует 13; RU `explodeProjectile:1594` принимает 6, обёртка — 10. Ошибка связывания аргументов возникает до тела try, поэтому может нарушить и штатное событие, а не только дополнительный рисунок.
- Эти два класса дефектов дополнительно подтверждены **изолированными Python2.7.18 AST/stub-проверками**: скаляр gravity отвергается; реальные RU количества аргументов отвергаются. Игра/полный мод не запускались.
- `showOwnVehicleHitDirection` совпадает по сигнатуре у EU и RU; это не компенсирует другие две обёртки.
- Обратный луч при отсутствии доступной сущности использует фиксированные 400 метров (`:59,190–208`). Это эвристическая линия направления, **не вычисленная точная позиция стрелявшего**.
- Время `maxShotDist / speed` и конечная полилиния не решают столкновения с terrain/объектами (`:168–186`). Нельзя обещать «полную фактическую траекторию» только из этого расчёта.
- Ссылка на паттерн Flock не подтверждает правильность выбранного ресурса: обе ветки `Flock.DebugLine` используют `helpers/models/unit_cube.model` (EU:64/RU:58), мод использует другой `res/objects/misc/bbox/unit_cube_1m_proxy.model` (`:47`). Наличие второго пути во всех игровых пакетах не проверено.
- Нет общего reset renderer на выходе из боя и отмены всех callbacks; события могут приходить быстро, 48 × 24 сегмента — до 1152 моделей только для линий. Верхняя граница не означает приемлемую производительность.

### Минимальные доработки

Для разрешённого тестового/обучающего сценария: отдельные EU/RU adapters с сохранением контракта оригинала, правильная нормализация типов, явный teardown, проверенный model resource, наблюдаемые ошибки вместо безусловного `except: pass`, тесты лимитов/повторного удаления. Пока это **P0: не устанавливать текущую реализацию в клиент**, особенно RU.

### Более качественный вариант

**Предложение:** начинать с визуализации собственных выстрелов в разрешённом тренировочном/аналитическом контексте; использовать расчёт траектории клиента там, где он подходит, отделять предсказание от реально полученных событий, переиспользовать пул сегментов, выполнять обновления с ограниченной частотой и полностью очищать состояние при смене arena. Обратный луч не выдавать за позицию противника.

Заявление о «легальности» нельзя выводить из самого использования Python API: [официальные категории RU](https://tanki.su/ru/content/guide/ban/nonusefulmods/) отдельно затрагивают изменение трассеров САУ и вычисление их позиции. [Политика EU](https://worldoftanks.eu/en/content/guide/fair-play/prohibited-mods/) тоже требует проверки конкретной механики. Это **не утверждение о выданной санкции конкретному моду**, а обязательное ограничение выбора функциональности. Доставка всех событий о скрытых целях в живом бою здесь не доказана; ReplayExposureLevel из entity_defs не следует трактовать как такую гарантию.

**Приоритет:** P0 исправить/исключить несовместимую загрузку, P3 для продуктового развития до определения допустимого сценария. Не переносить расширенный вражеский tracer на новую версию как обычное улучшение UI.

## Рекомендация по отдельным проектам

- Hello — использовать как короткий контроль загрузки, хранить один исходник.
- Overlay — сначала решить, нужен ли native компонент вообще; для обычного текста вероятно дешевле существующий UI.
- Tracers — не верить docstring без проверки данных/типов/политики; текущая реализация не готова ни к обещанной EU-функциональности, ни к загрузке в RU.
- Ничего из этих проектов автоматически не добавлять в десять активных spoter-mods. У каждого должен быть самостоятельный манифест, выбранный регион и критерии приёмки.
